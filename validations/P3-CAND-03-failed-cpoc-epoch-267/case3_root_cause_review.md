## What AlphaThreshold Means

`AlphaThreshold` is the cutoff used by the chain after a confirmation PoC. The
chain stores a `ConfirmationPoCRatio` for the participant, which is effectively:

```text
confirmed capacity / expected capacity
```

If that ratio is below `AlphaThreshold`, the participant fails confirmation PoC
and can be made inactive with reason `failed_confirmation_poc`.

For the confirmed claimant:

```text
ConfirmationPoCRatio = 0.0057419461588255
AlphaThreshold       = 0.5
```

That means the chain observed roughly `0.57%` of expected confirmation capacity,
while the required minimum was `50%`.

The relevant code path is:

```text
confirmation_poc.go:evaluateConfirmation()
  -> writes CurrentEpochStats.ConfirmationPoCRatio
calculations/status.go:getConfirmationPoCStatus()
  -> fails if ConfirmationPoCRatio < AlphaThreshold
participant_status.go
  -> records failed_confirmation_poc when status changes to INACTIVE
```

## Hardware/Config Alternative

A pure claimant hardware failure would usually predict one or more of:

- no submission for the failed cPoC;
- both models failing in the same way;
- repeated failure across later cPoCs;
- zero or obviously broken claimant validation activity around the same window.

The validation artifacts do not fit this pattern for the confirmed claimant:
the claimant submitted both Qwen and Kimi in cPoC #1, the exclusion was recorded
as `failed_confirmation_poc` in that cPoC window, and later Kimi submissions are
present. This does not fully disprove a proxy/config eligibility dispute, but it
does rule out the simple "claimant did not submit / hardware was generally
offline" explanation.

The exact status transition is visible in archive state:

- block `4122551`: claimant `ACTIVE`;
- block `4122552`: claimant `INACTIVE`;
- recorded reason: `failed_confirmation_poc`;
- `ConfirmationPoCRatio = 0.0057419461588255`;
- `AlphaThreshold = 0.5`;
- ratio is below alpha, so `calculations/status.go:getConfirmationPoCStatus`
  returns failure.

Plainly: the chain decided that the participant kept far less confirmed
capacity than required during that confirmation PoC.

## Simplified Root Cause

The participant submitted work, but the first Kimi confirmation PoC did not get
enough effective confirmation support. A large Kimi voting-power participant was
preserved for that same cPoC episode, so its Kimi nodes stayed out of validation.
That collapsed the claimant's confirmation weight from `65,716` to `343`, pushed
the ratio below the `0.5` threshold, and the chain excluded the claimant with
`failed_confirmation_poc`.
